# Собственная нейромодель автодополнения: проектные решения

Дата: 2026-10-06. Документ фиксирует решения, принятые при переходе от n-грамм к собственной нейромодели, и состояние
работ на эту дату. Числа без пометки — измерены на этом сервере; «оценка» — расчёт или экстраполяция, ещё не проверенная.
Отчёты по n-граммам: `REPORT-GO-RU.md`, `REPORT-CSHARP-RU.md`; обзор литературы: `RESEARCH.md`.

---

## 1. Что модель должна делать для разработчика

Три сценария, одинаковые для Go и C#; отличается только то, что язык даёт в качестве кандидатов.

1. **Ранжирование списка автодополнения.** Список строит плагин по PSI (все элементы корректны по типам), ML только
   переставляет. Сегодня это ranker над n-граммной LM: Go на реальных списках плагина MRR 0.783 / top-1 0.675 против правил
   плагина 0.534 / 0.394. Нейромодель добавится как признак ranker'а (log-prob кандидата в контексте).
2. **Серая подсказка (ghost text) — целая строка.** Сегодня n-граммы (e13): показ в 9 % позиций, 90 % верных, длина 2–3 токена
   (`.Close()`, `!= nil {`). N-граммы не видят дальше 4 токенов назад и не знают имён переменных — целую строку они не соберут.
   Нейромодель с контекстом 2048 токенов и fill-in-the-middle должна собирать строки из того, что есть в файле:
   `return fmt.Errorf("open %s: %w", path, err)`, `defer mu.Unlock()`, `_logger = logger;`,
   `throw new NotFoundException($"User {id} not found");`. Оценка: точное совпадение строки в 25–35 % позиций, ещё 20–30 % —
   верная структура с другим именем/литералом.
3. **Текст внутри строковых литералов** — сообщения логов и ошибок, format-строки с плейсхолдерами по аргументам
   (`"failed to open %s: %v", path, err`; `"Failed to process order {OrderId}", order.Id`), struct-теги (`json:"user_id"`),
   атрибуты (`[Route("api/[controller]/{id}")]`). Для этого токенизатор **сохраняет строки и комментарии** (лексер n-грамм
   схлопывает их в `<STR>`). Конкретные значения (адреса, ключи) модель предлагать не должна — корпус чистится от секретов.
4. **Позже** — «маппинги» `dto.Name = entity.Name` как PSI-кандидаты + ranker (пункт 4 общего плана).

Чего модель не делает: функции по описанию, код из других файлов проекта (только контекст), сеть. Все кандидаты списка —
из PSI; модель ничего не выдумывает в списке, только в ghost text.

## 2. Ограничения, которые определяют конструкцию

- **Никаких сторонних моделей и нативных рантаймов** в плагинах: обучение — PyTorch на сервере, инференс — чистый Kotlin
  в `ml-core`. У пользователя один артефакт — файл модели `.cml` в ресурсах плагина.
- **JBR не содержит Vector API.** Проверено 2026-10-06 на IntelliJ 2026.x / JBR 25.0.3 (macOS): `jbr/bin/java --list-modules`
  не содержит `jdk.incubator.vector` (вообще ни одного инкубаторного модуля); `--add-modules=jdk.incubator.vector` в vmoptions
  **ломает запуск IDE**. Следствие: **production-путь инференса — скалярный Kotlin** с авто-векторизацией C2 и многопоточностью;
  Vector API из `ml-core` удалён 2026-10-07 (остались scalar и наши нативные ядра). Побочный урок: строка vmoptions с пробелом (`--add-modules jdk.incubator.vector`)
  молча игнорируется — одна строка = один аргумент JVM.
- **Ничего не требовать от пользователя**: ни vmoptions, ни установки рантаймов. Опционально плагин может предложить
  правку vmoptions через `com.intellij.diagnostic.VMOptions` (как «Change Memory Settings»), но работать должен и без неё.
- **Без preview-API в `ml-core`** (FFM в JBR 21 — preview): веса в off-heap `ByteBuffer`/массивах.
- Rider/GoLand решают это иначе: Full Line Completion — нативный llama.cpp, поставляемый вместе с IDE, флаги JVM в
  product-level vmoptions. Плагину это недоступно.

(`tools/server/prepare-disk.sh`).

## 4. Токенизатор (готов для Go, паритет подтверждён)

Byte-level BPE, свой тренер на Python и свой энкодер на Kotlin (`ml-core/.../bpe/BpeTokenizer.kt`), без сторонних библиотек.
Претокенизатор `go-code-1` — ручной байтовый сканер, одинаковый на обеих сторонах:
- классы байтов: L = `[A-Za-z_]` и всё ≥0x80 (не-ASCII и эмодзи — «буквы»), D = цифры, W = пробел/таб, N = CR/LF, P — прочее;
- перевод строки вместе со следующим отступом — один претокен (`"\n\t\t"`); хвостовой пробел перед словом прилипает к слову;
- единица: необязательный пробел + `L+` | одна цифра | `P+`; претокены >128 байт режутся;
- camelCase/snake_case не режутся — подслова учит BPE; буквы, цифры и пунктуация не склеиваются через границу класса
  (`int32` → `int 3 2`); строки и комментарии — как есть; невалидный UTF-8 проходит без потерь.

Словарь: id 0–255 — байты, далее слияния, последние 16 — спец-токены (`<|endoftext|>`, `<|fim_prefix|>`, `<|fim_middle|>`,
`<|fim_suffix|>`, `<|file_sep|>`, `<|repo_name|>`, `<|pad|>`, резерв). Текст никогда не порождает спец-токен. Формат файла —
текстовый `CMLBPE 1` (16k: 137 КБ); 16k-словарь — префикс 32k.

| Словарь | Байт/токен (Go test) | Токенов vs лексер | Оценка lm-фолда Go |
|---|---|---|---|
| **16 384** | 3,16 | 1,80× | **6,80 млрд** |
| 32 768 | 3,28 | 1,73× | 6,55 млрд |

**Выбран 16k**: 32k экономит 3,8 % токенов, но удваивает embedding и выходную матрицу — для int8-инференса на CPU дороже.
Паритет: 10 571 кейс (571 синтетических: пустой ввод, CRLF, NUL, невалидный UTF-8, эмодзи/ZWJ, BOM, строки 5 000 символов,
литеральный `<|endoftext|>` + 10 000 файлов test-фолда), 21,66 млн id совпали, round-trip точный. Скорость Kotlin-энкодера
~84 МБ/с в один поток. Большая фикстура (31 МБ) живёт вне репо (`~/work/ml-data/tokenizer/parity-go`, env `CML_BPE_FIXTURE`),
маленькая (0,28 МБ) — в `ml-core/src/test/resources/bpe`. Для C# обучается свой словарь тем же претокенизатором (Go-словарь
на C# даёт 3,92 байта/токен — работает, но хуже).

## 5. Архитектура модели

Декодер «Llama-стиль», минимум операций для Kotlin: pre-norm **RMSNorm**, **RoPE**, **SwiGLU** MLP, **GQA** (меньше KV-голов →
компактнее KV-кэш), связанные embedding/выход, без bias. Словарь 16 384, контекст 2048 при обучении. Отдельная модель на язык.

| Конфигурация (ориентир) | Параметров | Веса int8 | Декод, 8 ядер скалярно (оценка) | Prefill 512 токенов (оценка) |
|---|---|---|---|---|
| d384 × 8 слоёв | ~30 М | 30 МБ | 2–3 мс/токен | 0,3–0,6 с |
| d512 × 8 | ~50 М | 50 МБ | 3–5 мс/токен | 0,5–1 с |
| d768 × 10 | ~100 М | 100 МБ | 5–10 мс/токен | 1–2 с |

Размер решает бенчмарк скалярного Kotlin-инференса на случайных весах (агент D, в работе), а не априорная цифра.
Бюджет: строка из 20 токенов ≤150 мс и первая подсказка на холодном файле ≤1 с на 8-ядерном ноутбуке (AVX2 и Apple Silicon).
Узкое место — не декод, а **prefill**; 100 М параметров остаются целью, если prefill укладывается (см. §7) — иначе 30–50 М.
Ожидаемый выигрыш 30 → 100 М: ppl −10–15 %, точная строка +5–8 п.п. (оценка по литературе о малых кодовых моделях).
Качественный скачок относительно n-грамм даёт уже 30 М — за счёт длинного контекста и FIM.

## 6. Обучение

- Данные: lm-фолд в BPE-шардах; упаковка в 2048 с `<|file_sep|>`; **FIM в ~50 % примеров** (PSM/SPM на уровне документа) —
  при редактировании середины функции модель видит код после курсора и не предлагает уже написанное.
- Понижающий вес больших однообразных репозиториев (SDK-обёртки): выбор файлов с весом ∝ 1/√(токенов репо), с капом.
- AdamW β=(0.9, 0.95), wd 0.1, cosine LR с разогревом, bf16, grad clip 1.0, 1–2 эпохи. Оценка: 30 М — ~2 ч на эпоху по 6,8 млрд
  токенов на RTX PRO 6000 (6·N·D ≈ 10¹⁸ FLOP при ~150 TFLOPS реальных); 100 М — ~6 ч.
- Метрики: ppl на test-фолде; главная — `ml-train eval-inline` в тех же условиях, что e13 (доля позиций с показом при
  уверенности ≥ порога и точность), плюс отдельная метрика точности внутри строковых литералов.
- **FIM и окна (урок go31m, шаг 2500).** Первая оценка показала PSM-формат сломанным (2 % верных строк при 62 % у SPM и plain).
  Причина — не формат, а нарезка: документы склеивались и резались на окна по 2048 где попало, а файлы длинные (lm Go: медиана
  1 023 BPE-токена, среднее 2 158, **74,5 % токенов — в файлах длиннее окна**). В PSM середина стоит после всего суффикса, и в окно
  с серединой префикс обычно не попадал — модель выучила его игнорировать; в SPM префикс вплотную к середине и всегда в окне.
  Исправление: FIM-документ ограничен (суффикс ≤512, середина ≤256, префикс — хвост до ≤2048 суммарно), упаковка не режет
  FIM-документ границей окна, часть вырезок выровнена по строкам; промпт инференса ≤2048 суммарно. Тесты: «`<|fim_prefix|>` и
  `<|fim_middle|>` в одном окне», обратная сборка `pre+mid+suf == body`, точный resume. **Чеклист для C#**: та же `data.py`, но
  проверить распределение длин файлов в C#-шардах, дамп FIM-окон на C#-данных и границы строк при CRLF.
- Экспорт: `export.py` → секция нейромодели в `.cml`: int8-веса с масштабом на выходную строку (embedding тоже int8),
  нормы float32, конфиг в заголовке, словарь BPE в том же файле. Формат — `docs/NN-FORMAT.md` (пишется агентом D).
- Порядок: сначала **30 М** (отладка пайплайна, экспорта, инференса, метрик), затем 100 М той же конфигурацией, если бенчмарк
  позволил; промежуточно 50 М. Вариант «две модели, настройка fast/quality» — по факту, цена — удвоение дистрибутива.

## 7. Инференс в `ml-core` и ускорения на стороне плагина

Ядро: загрузка `.cml` в off-heap, int8×float matvec многопоточно по строкам (формы циклов под авто-векторизацию C2:
независимые аккумуляторы, без проверок границ), KV-кэш, RoPE, causal attention, greedy/top-k, log-prob на токен для порога
уверенности. Проверка корректности — инкрементальный декод против наивного полного пересчёта на крошечной конфигурации.

Что ускоряет сильнее всего — живёт в плагине, а не в модели (по убыванию эффекта):
1. **Инкрементальный KV-кэш между нажатиями**: между двумя нажатиями контекст меняется на несколько токенов — досчитываем хвост;
   при прыжке курсора переиспользуем общий префикс; полный prefill — только при открытии файла, в фоне.
2. **Сжатие контекста через PSI**: импорты, сигнатуры типов/функций файла, тело текущей функции целиком, тела остальных —
   выброшены; контекст в 3–5 раз короче, prefill — пропорционально. Требует подавать часть обучающих примеров в таком же виде
   и, значит, решается **до** обучения. Сюда же — сигнатуры из других файлов проекта (тип переменной под курсором).
3. **Спекулятивное декодирование с n-граммами как черновиком**: n-граммы предлагают 4–6 токенов за микросекунды, трансформер
   проверяет их одним проходом (матрица×матрица эффективнее на JVM, чем шесть матрица×вектор); результат идентичен,
   на шаблонном коде декод ×2–3.
4. **Ограничение словаря кандидатами из PSI** при дополнении идентификатора — и быстрее, и модель не предложит несуществующее.
5. JVM-инженерия: прогрев JIT в фоне при старте, пул потоков по числу ядер, ранний выход при падении уверенности, debounce
   150–300 мс с отменой, кэш ответов по хэшу контекста.
6. int4 с группами по 32 — проверить на Apple Silicon (широкая память); на x86 JVM упирается в вычисления.

**Нативные ядра (не решено).** Если 100 М не укладывается скалярным Kotlin: свои ~500–1000 строк C (int8 matvec/matmul
AVX2/AVX-512/NEON, softmax, RMSNorm) через JNI; 4 бинаря (win x64, linux x64, mac arm64/x64) кросс-компиляцией `zig cc`;
подпись/нотаризация на macOS, риск ложных срабатываний антивирусов на Windows, краш в native убивает IDE (нужен фаззинг
и обязательный fallback на Kotlin). Выигрыш ×3–5 (оценка). Это не «чужой рантайм», но изменение принятого ограничения —
решение за пользователем, после цифр бенчмарка.

## 7a. Первая модель: go31m-e1 (2026-10-06)

d512 × 8 слоёв, 30,9 М параметров, словарь 16k, 1 эпоха = 6,8 млрд токенов, 2,5 ч на RTX PRO 6000 (771k ток/с, bf16, compile).
Первые 62 % эпохи — со сломанным PSM (см. §6), остаток — с исправленным. Итог: ppl 2,13 (plain, test-фолд);
экспорт в `.cml` 31 МБ, int8 без потерь (ppl 2,131 → 2,131). Модель: `~/work/ml-data/go/models/go-nn-31m-e1.cml`.
Обучена на корпусе **без** фильтра секретов — для внутреннего сравнения, в плагин не идёт.

`eval_inline` (3 000 позиций test-фолда по протоколу n-граммного `eval-inline`, `~/work/nn/eval/eval_inline.py`):

|---|---|---|---|
| Показ при точности ≈95 % (целая строка верна) | 10,0 % (≥3 токена 92,9 %) | **32,1 %** (prod ≥0,8: ≥3 токена 96,7 %, строка 95,4 %) | ≈ то же |
| Показ при точности ≈90 % | 16,5 % (83,3 %) | 45,7 % (93,1 %) | — |
| Остаток строки целиком, ≤8 токенов осталось | 35,1 % | 63,2 % | **65,8 %** |

## 7c. Token healing и политика показа (2026-10-07)

**Проблема.** Протокол `eval_inline` ставит курсор после лексического токена; если следующий символ — тоже пунктуация
(`foo(⟨⟩)`, `"x"⟨⟩)`, `foo()⟨⟩;`), промпт обрывается *внутри* пре-токена BPE (`()`, `")`, `);` — один пре-токен), чего в
обучении не бывает. Таких позиций 9,7 % в Go и 10,9 % в C#, модель угадывала в них 1,5–4,8 % строк. То же самое, ещё
острее, случается у живого плагина: промпт, оканчивающийся набранным пробелом, даёт 0,4 % верных строк (пробел
приклеивается к следующему слову), а курсор посреди идентификатора (`e.Hi⟨⟩`) — обрыв внутри слова.

**Решение — token healing** (реализовано и в Python-harness'е, и в Kotlin `ml-core/nn`): промпт режется назад до
последней границы пре-токена ≤ курсора (сканер cmlbpe по текущей строке, с байтом `\n` перед ней — токен перевода строки
владеет отступом — и до конца строки за курсором: что идёт после курсора, решает, где кончается пунктуационная серия
или слово). Байты между границей и курсором («набранный остаток»: `(`, `)`, `"`, `()`, пробел, `Hi`…) становятся
ограничением на декодирование: пока остаток не воспроизведён, словарь маскируется до токенов, которые начинаются с
остатка или являются его префиксом (тогда ограничение продолжается остатком остатка); вероятности берутся из
маскированного softmax; набранные байты отрезаются от результата. Таблица префиксов словаря — отсортированный массив
байтовых строк токенов + бинарный поиск, строится один раз (`VocabPrefixIndex`), результат кэшируется по остатку.

**Политика показа** (измерена на 3 000 позиций): порог по `conf_prod` — произведению вероятностей всех токенов строки
вместе с переводом строки (а не `conf_gm3` / `conf_min`); не показывать чисто пунктуационные подсказки (`);`, `}`, `)]` —
без буквы, цифры и кавычки); защита от повторов — n-грамма BPE-токенов (n ≤ 4, ≥ 4 байт) трижды подряд останавливает
декодирование, и такая строка, как и упёршаяся в лимит 48 токенов, не показывается.

**Числа** (`~/work/ml-data/go/nn/eval-heal.md`; 3 000 позиций, SPM; `--heal none` воспроизводит прежние прогоны побайтно):

| | Go go31m-e1: без → с healing | C# cs31m-e1: без → с healing |
|---|---|---|
| Остаток строки целиком, все позиции | 55,7 → **61,7 %** | 39,8 → **47,9 %** |
| Остаток строки целиком, ≤ 8 токенов | 65,8 → 73,3 % | 49,0 → 60,2 % |
| Первый лексический токен | 0,798 → 0,875 | 0,718 → 0,810 |
