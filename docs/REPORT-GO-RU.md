# Отчёт: ML-ранжирование автодополнения для Go

Дата: 2026-10-05. Репозиторий движка: https://github.com/dvislobokov/idea-ml-completion (подключён в `idea-golang-support`
как git subtree `ml/`). Подробности каждого эксперимента — в `CHANGELOG.md`, методика — в `docs/RESEARCH.md`,
контракт адаптера плагина — в `docs/ADAPTER.md`.

## 1. Что сделано

1. **Языковая модель** (L2): n-граммная модель порядка 4 с модифицированным сглаживанием Кнезера–Нея, компактное
   хранение (24-битные отпечатки, 8-битные квантованные значения), плюс кэш-модель текущего файла, смешиваемая с
   глобальной (λ=0.3). Это даёт признак «вероятность кандидата по контексту».
2. **Ранкер** (L1): линейная модель над 13 общими признаками (вероятность по LM, ранг по LM внутри списка, частота и
   давность идентификатора в файле, совпадение регистра с префиксом, длина имени, размер списка и т. д.) × 6 типов
   контекста (после точки, начало оператора, аргумент, позиция типа, правая часть присваивания, прочее). Обучается
   попарно на списках кандидатов, инференс 0.12 мкс на кандидата, файл модели 4 КБ.
3. **Адаптер Go-плагина**: 17 PSI-признаков из настоящего completion плагина (вид кандидата, уровень области
   видимости, нужен ли импорт, совпадение с ожидаемым типом, объявлен ли в этом файле и как далеко, позиция по
   текущим правилам плагина). Headless-экспорт датасета через `./gradlew :go-psi-ide:mlDataset`, тест паритета
   признаков между экспортом и точкой расширения `completionRanker`.
4. **Серверный конвейер** на AMD EPYC 24 ядра / 64 ГБ: загрузка корпуса (через tarball, git-протокол GitHub с
   этого хостинга не работает), детерминированное разбиение репозиториев на доли, обучение, сводный отчёт.

Методика измерения везде одна: разбиение **по репозиториям** (тестовые репозитории не видны ни LM, ни ранкеру),
дедупликация файлов (Jaccard ≥ 0.8), кэш файла λ=0.3, **кросс-фиттинг** — LM и ранкер обучаются на непересекающихся
долях репозиториев (иначе ранкер переучивается на «знакомый» LM и теряет 0.03 MRR на новых репозиториях).

## 2. Корпус

| | локально | сервер |
|---|---|---|
| репозиториев Go | 33 | 900 (1,07 млн файлов, 11,1 ГБ) |
| доли: тест / LM / ранкер | 4 / 19 / 10 | 30 / 580 / 290 |
| файлов после дедупликации для LM | 16,5 тыс. | 259 тыс. (349 млн токенов) |
| дубликатов удалено | 5 % | 7 % (6,5 тыс. точных, 12,5 тыс. близких) |

Тестовые репозитории на сервере — 30 случайных по md5 имени (pluto, cilium/ebpf, cfssl, kube-router и др.),
оценка LM на 3664 файлах из них, ранкер — на 46 тыс. списков.

## 3. Языковая модель: локально → сервер

| модель | репо для LM | n-грамм | размер | перплексия | OOV идентификаторов | top-1 / top-5 следующего идентификатора |
|---|---|---|---|---|---|---|
| локальная (e07) | 19 | 2,5 млн | 30 МБ | 5,5 | 29,4 % | 0.440 / 0.682 |
| сервер, 100 репо | 100 | 5,3 млн | 53 МБ | 5,1 | 24,1 % | 0.453 / 0.713 |
| **сервер, 580 репо, без отсечения** | 580 | 27,1 млн | 163 МБ | **5,0** | **21,5 %** | **0.468 / 0.720** |

Перплексия и OOV меряются только на идентификаторах в словаре (50 тыс. слов). Рост корпуса в 30 раз дал −0.5
перплексии и −8 п. п. OOV; дальнейший рост упирается в словарь, а не в число n-грамм. Время: подсчёт 349 млн токенов
5 минут, оценка 80 секунд, пик памяти 23 ГБ.

Отсечение редких n-грамм (серия `prune-*`, чтобы уложить модель в 20–40 МБ для плагина): результаты в разделе 7.

## 4. Ранкер на прокси-списках (без PSI)

Списки кандидатов здесь синтетические: все идентификаторы файла и топ LM с тем же префиксом, в среднем 28–31
кандидат. Это измеряет сам движок, а не плагин.

| | локально (e07) | сервер, полный корпус |
|---|---|---|
| списков обучение / тест | 170 тыс. / 55 тыс. | 731 тыс. / 46 тыс. |
| **ранкер MRR / top-1 / top-5** | 0.718 / 0.604 / 0.861 | **0.739 / 0.629 / 0.876** |
| только LM | 0.551 | 0.575 |
| самый частый в файле | — | 0.409 |
| самый недавний в файле | — | 0.400 |
| по алфавиту | — | 0.141 |

Вывод: на полном корпусе ранкер +0.02 MRR, LM-only +0.025. Основной вклад дают признаки внутри файла (регистр
префикса, в словаре ли, давность) и LM; объём данных для ранкера не узкое место, узкое место — признаки.

## 5. Ранкер на настоящих списках Go-плагина (PSI)

Экспорт локально: 7 репозиториев для обучения (12 тыс. списков), 4 отложенных — caddy, etcd, esbuild, v2ray-core
(7811 списков, в среднем 49 кандидатов). 30–160 мс на позицию, LM из локальной доли.

| порядок списка | top-1 | top-5 | MRR |
|---|---|---|---|
| правила плагина (ожидаемый тип → область видимости → имя) | 0.394 | 0.699 | 0.534 |
| только LM | 0.342 | 0.532 | 0.439 |
| самый частый в файле | 0.353 | 0.727 | 0.516 |
| **ML-ранкер, 210 весов** | **0.675** | **0.919** | **0.783** |

По типам контекста ранкер даёт MRR от 0.735 (после точки) до 0.812 (начало оператора). Правила плагина слабее всего
после точки (0.378: члены одного уровня сортируются по имени) и в позиции типа (0.407). Самые тяжёлые веса: точное
совпадение регистра с префиксом, объявлен в этом файле, уровень области видимости, нужен импорт, вид «ключевое слово»
(отрицательный).

Важная оговорка: `rule_rank_log` воспроизводит вейгер плагина, но не стандартные вейгеры платформы (префикс, близость),
идущие после него, так что строка «правила плагина» немного пессимистична. Практически это значит: нужный элемент
попадает в первую строку в 2 случаях из 3 вместо 2 из 5, в первые пять — в 92 % вместо 70 %.

**Полнота кандидатов** плагина: 88–92 % позиций содержат нужный идентификатор в списке; в остальных его нет вовсе
(ранкер здесь бессилен). Это отдельный резерв для самого completion.

## 6. Что это стоит в IDE

- Модель ранкера 4 КБ, оценка списка из 50 кандидатов — микросекунды.
- Языковая модель: 163 МБ без отсечения — много для плагина; цель 20–40 МБ (см. раздел 7). Оценка одного кандидата
  по n-граммам — константное число хеш-поисков, кэш файла обновляется по токенам редактора (~1 мкс на токен).
- Признаки PSI считаются из тех же объектов, что уже есть у `GoCompletionWeigher`, дополнительных обходов PSI нет;
  единственный потенциально дорогой — смещение объявления, и он берётся только для объявлений в текущем файле.

## 7. Отсечение n-грамм на полном корпусе

Серия на сервере, 580 репозиториев для LM, те же 30 тестовых. `--min-count a,b,c,d` — минимальное число вхождений
по порядкам 1..4, `--min-repos` — минимальное число репозиториев, где n-грамма встречалась (отсекает код одного проекта).

| вариант | n-грамм | размер | перплексия | top-1 / top-5 | ранкер MRR / top-1 / top-5 |
|---|---|---|---|---|---|
| без отсечения | 27,1 млн | 163 МБ | 5,0 | 0.468 / 0.720 | 0.739 / 0.629 / 0.876 |
| count 1,1,2,2 | 12,8 млн | 78 МБ | 5,0 | 0.470 / 0.722 | 0.739 / 0.629 / 0.876 |
| count 1,2,3,3 | 8,1 млн | 50 МБ | 5,1 | 0.470 / 0.722 | 0.738 / 0.629 / 0.875 |
| count 1,1,2,2 + repos 1,1,1,3 | 5,9 млн | 35 МБ | 5,0 | 0.480 / 0.727 | 0.738 / 0.628 / 0.874 |
| count 1,1,3,3 + repos 1,1,2,5 | 3,4 млн | 20 МБ | 5,1 | 0.481 / 0.727 | 0.737 / 0.627 / 0.873 |
| **порядок 5, count 1,1,3,3,3 + repos 1,1,2,5,5** | 4,5 млн | **27 МБ** | **4,7** | **0.497 / 0.738** | **0.742 / 0.636 / 0.874** |

Модель сжимается в 8 раз при потере 0.002 MRR; точность по следующему идентификатору даже растёт на 1 п. п.,
потому что отсечение по числу репозиториев убирает n-граммы, специфичные для одного проекта (они на чужом коде только
мешают). На локальном корпусе из 19 репозиториев такое отсечение стоило до 1 п. п. top-1 (e03): порог по репозиториям
имеет смысл только на большом корпусе. С тем же отсечением порядок 5 даёт ещё −0,4 перплексии и +1,6 п. п. top-1 за
7 МБ: на 19 репозиториях он себя не окупал (e06), на 580 окупает. Рекомендация для плагина: порядок 5 с отсечением
`--min-count 1,1,3,3,3 --min-repos 1,1,2,5,5`, 27 МБ.

## 8. Как попробовать в IDE

В Go-плагине (0.2.179) ML-часть собирается по флагу: `./gradlew.bat runIde -PmlEnabled=true -Pml.models=<каталог>`
(или `buildPlugin` для zip; флаг можно задать и переменной `MLENABLED=true`). В каталоге лежат `lm.cml` и `rank.cml`.
В такой сборке появляется страница Settings | Go | Smart Completion с выключателем и полем «каталог моделей» (чтобы
подменить модели новым обучением без пересборки). Сборка без флага не содержит ни ранкера, ни страницы. Модели
загружаются в фоне при первом вызове автодополнения, до этого действует прежний порядок. Проверено тестом
`GoMlCompletionRankerTest`: все Go-кандидаты получают оценку, первая подсказка после загрузки — ожидаемый параметр.

Важно: `rank.cml` обучен на признаках конкретной `lm.cml` (e07, локальная), поэтому пока в IDE идёт эта пара. Чтобы
использовать серверную модель 27 МБ, ранкер нужно переобучить на экспорте с ней (пункт 1 ниже).

## 9. Следующие шаги

1. Переобучить ранкер на экспорте с серверной LM (порядок 5, 27 МБ) и положить пару в сборку.
2. Экспорт PSI-датасета на сервере по долям `sets/rank.txt` / `sets/test.txt` (нужны IDEA Community и Go toolchain
   на сервере), обучение ранкера на сотнях репозиториев вместо 7.
3. Замер задержки ранкера в IDE на больших файлах (токенизация текста до каретки при каждом вызове; при необходимости
   кэш состояния файла по штампу документа).
4. Дедупликация на уровне шардов (v2fly/v2ray-core и v2ray/v2ray-core — один код в разных долях).
5. Разобраться с репозиториями, где экспорт дал 0 списков (headscale: нет `go.mod` в корне).
6. Повышение полноты кандидатов плагина (10 % позиций без нужного элемента в списке).
