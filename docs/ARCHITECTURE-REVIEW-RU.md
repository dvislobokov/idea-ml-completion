# Архитектура go31m/cs31m: почему так и что улучшить (обзор, 2026-10-07)

Источник: чтение `docs/NEURAL-RU.md`, `docs/RESEARCH.md`, `docs/NATIVE-KERNELS.md`, `CHANGELOG.md` (e14–e17), `tools/nn/train/{model,data,train,export}.py`, `ml-core/.../nn/*.kt`. Код не запускался.

## Расхождения с постановкой задачи
- Все измерения обучения сделаны на одной RTX PRO 6000 (771k ток/с). DDP в `train.py` нет, скорость на H200 не измерялась.
- 3,9 G (Go) и 2,95 G (C#) — токены лексера; в BPE модель обучалась на 6,84 G (Go) и 5,65 G (C#, очищенный корпус).
- Таблица §5 `NEURAL-RU.md` («d384×8 ≈ 30 M, d512×8 ≈ 50 M») устарела: по пресетам `model.py` d384×8 = 18,9 M, d512×8 = 30,9 M.

## Ограничения
1. Только своя модель, PyTorch для обучения, Kotlin-инференс, один файл `.cml`.
2. В JBR нет `jdk.incubator.vector`: продакшен — скалярный Kotlin. C-ядра дают ×3–4, решение о поставке не принято. Kotlin принимает только `swiglu` + `rmsnorm` (`NnConfig.kt`). Декод только жадный, один KV-кэш — beam не поддержан.
3. Латентность: строка из 20 токенов ≤ 150 мс, холодный файл ≤ 1 с на 8-ядерном ноутбуке. Узкое место — prefill.
4. Размер: int8, 31 МБ (n-грамма — 32 МБ).
5. Один прогон 31 M на PRO 6000: 2,5 ч (Go), 123 мин (C#).
6. 1 эпоха = 6,8 G токенов; запаса данных на многократное переобучение нет. Rank-фолд Go (3,2 G) зарезервирован под ранкер.

## Почему так

| Выбор | Причина | Где измерено |
|---|---|---|
| 31 M (d512×8) | Самая большая модель в бюджете на скалярном пути; «первая модель для отладки пайплайна», не оптимум | NnBench (`NATIVE-KERNELS.md`): строка целиком скалярно S30M 148 мс / M48M 208 / L99M 534; native q8 46 / 67 / 122. e16: оценка для ноутбука 30M ≈ 65 мс native (150 скалярно), 48M ≈ 105, 100M ≈ 200 |
| 8 слоёв, head_dim 64 | Рекомендация обзора («6–8 слоёв, d384–512»), удобство ядер. Абляции нет | `RESEARCH.md` §8, `model.py` |
| SwiGLU 1408 (≈8/3·d) | Стандарт Llama, минимум операций для Kotlin. Не сравнивалось | `NEURAL-RU.md` §5 |
| GQA 8 Q / 2 KV | Компактный KV-кэш на CPU: f32 на 2048 токенов 16,8 МБ против 67 МБ при MHA. Эффект не измерен | `model.py` |
| RoPE θ=1e4, RMSNorm, без bias | Llama-стиль, простые операции. Не сравнивалось | `NnModel.kt` |

| Словарь 16k | 32k даёт лишь −3,8 % токенов, но ×2 эмбеддинг и голову; у FLCC тоже 16 384 | §4, `RESEARCH.md` §6 |

## Что улучшить

Цена: `flops_per_token` из `model.py`: 50M ≈ ×1,6, 102M ≈ ×2,9 относительно 31M (≈4 ч и ≈7,3 ч/эпоху на PRO 6000).

| Идея | Эффект | Цена | Риск | Приоритет |
|---|---|---|---|---|
| Без обучения: префикс 512/1024/1450; beam/повторная выборка с гейтом `conf_prod` в Python-harness | Кривая качество↔prefill; у FLCC beam с приоритетом гипотез, завершённых `\n`, поднял perfect lines 13→21 % | минуты GPU | нет | **1** |
| NnBench конфигураций-кандидатов на ноутбуке (скалярно и native) | Реальный бюджет для 50M, глубокой-узкой, MQA | часы без GPU | нет | **1** |
| SPM-доля 0,8–1,0 при FIM 0,7–0,9 | Ёмкость не тратится на неиспользуемый PSM; FIM почти бесплатен для plain (Bavarian et al.) | 1 прогон | проверить plain-режим | **2** |
| lr 2e-3, батч 0,25–0,5 M | Скейлинг-фит DeepSeek LLM для C≈1,6e18: lr≈1,6e-3, батч≈0,3 M | 1 прогон | нестабильность (есть clip) | **2** |
| Глубокая-узкая d384×14, 6/2 головы, ~28 M | MobileLLM: глубина важнее ширины <1B; меньший эмбеддинг | 1 прогон | декод упирается в диспетчеризацию (~45 регионов/токен): больше слоёв — медленнее. Сначала NnBench | 2–3 |
| 31M×2 эпохи vs 50M×1 эпоха (равный compute) | Muennighoff: до ~4 эпох повторы ≈ уникальные. При 220 ток/параметр 31M скорее ограничена ёмкостью → ждать больше от 50M | ~5 ч каждый, параллельно | 50M скалярно 208 мс/строка — выше бюджета; нужны native или PSI-сжатие | **3** |
| lm+rank = ~10 G токенов Go вместо 2-й эпохи | лучше повторов | как 1,5 эпохи | утечка, если log-prob модели станет признаком ранкера | 3 |

## Рекомендуемый порядок (по одному изменению; две карты = два прогона)
0. Без обучения: префикс 512/1024/1450, beam k=2–3 в harness, NnBench кандидатов на ноутбуке.
1. A: новый Go-baseline (очищенный корпус, FIM 0,7 с первого шага; старая go31m 62 % эпохи училась со сломанным PSM). B: то же, SPM-доля 1,0.
2. A: lr 2e-3, батч 0,5 M. B: d384×14.
3. A: 31M×2 эпохи. B: 50M×1 эпоха.
4. Лучший рецепт → C#. Затем формат с PSI-контекстом.
5. Учитель/дистилляция или 100M — после решения о native-ядрах.

Сравнивать по `eval_ppl`/`eval_fim_ppl` и `eval_inline` с healing. Стандартная ошибка на 3000 позициях ≈0,9 п.п.: разницы <2 п.п. — шум; нужно 10k позиций или парное сравнение.

## Не измерено
- Абляции глубины/ширины, GQA/MQA/MHA, долей FIM/SPM, длины контекста, lr и батча — ни одна настройка не сравнивалась.
- Кривая loss по токенам (насыщается ли 31M к концу эпохи); эффект 2-й эпохи; разброс по сидам.
- Латентность на реальном ноутбуке (x86, Apple Silicon) на обученной модели; загрузка NEON/Windows/macOS.
- Память KV-кэша и сессий в IDE; качество int4; скорость на H200 и DDP; acceptance rate у пользователей.
- Сравнение Go/C# смешано с разницей рецепта (FIM 0,5 vs 0,7, сломанный PSM в go31m).
